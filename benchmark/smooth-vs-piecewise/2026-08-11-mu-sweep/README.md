# Smooth vs piecewise primitives: mu sweep

Comparison of the two CommonMath primitive families across the shared
sharpness scale mu, for a journal paper/letter. The smooth family is the
existing C-infinity tanh/softplus set; the piecewise family composes the same
primitives exactly from fmax with a piecewise-linear step of slope mu
(`math.mode` in the study file selects the family at runtime, `math.mu` sets
the scale; see `application/PhasorDynamics/README.md`).

## Arms

- **smooth**: the existing C-infinity primitives, swept over 9 half-decade
  mu values in [1e0, 1e4] (3 values on the coarse tier).
- **piecewise**: one pinned reference model per case. Its ramp/qramp family
  is exact and mu independent by construction; its step gates (anti-windup,
  deadbands, indicators) are piecewise linear with slope `math.gate_mu`,
  pinned at 1e4 for every run so the arm represents a single fixed
  approximation of the discrete model. The truly discontinuous gate is the
  gate_mu -> infinity limit and requires integrator event detection (out of
  scope here by design, reserved in the Smoothing enum).

Each cell runs at the default tolerance (1e-5/1e-7) for the measured point
and at tight tolerance (1e-9/1e-11) as a reference: the tight piecewise run
is the exact-model reference for every smooth run of its case; the tight
same-mode run isolates pure integration error.

## Matrix

Generated by `make_matrix.py` under `work/` (gitignored), executed by
`run_matrix.py` (single pinned core, resumable), aggregated by `analyze.py`
into `results.csv`; figures by `make_figures.py`.

 Tier   | Cases                                                         | smooth mu grid           | piecewise
 -------|---------------------------------------------------------------|--------------------------|-----------
 dense  | TwoBusTgov1, TwoBusGensal, TwoBusIeeet1, ThreeBusBasic, ACTIVSg200, ACTIVSg500 | 9 points 1e0..1e4 | pinned arm
 coarse | WECC240, ACTIVSg10k                                           | 1e0, 1e2, 1e4            | pinned arm

## Captured per run

- `ida_stats.json`: per-segment and total steps, residual/Jacobian
  evaluations, linear solver setups, error-test failures, nonlinear
  iterations/failures.
- `ida_steps.json`: every accepted step's size, order, cj, per-step work
  deltas, and the WRMS local truncation error (`lte_wrms`, 1.0 = at the
  error-test limit).
- `stdout.txt`: `GRIDKIT_PROFILE` and `SYSTEM_RESIDUAL_PROFILE` timing
  blocks, system size, and the `math_mode`/`math_mu`/`math_gate_mu`
  provenance echo.
- `study_out.csv`: monitor trajectories on the shared `dt_monitor` grid,
  used for cross-run trajectory error.

## Results

136 runs, 130 completed; every failure is one of the two boundary findings
below. `results.csv` holds the full matrix; `matrix-run.log` is the raw run
record. Trajectory errors are WRMS over all monitored columns on the shared
monitor grid against the case's pinned tight-tolerance piecewise arm
(`ref_model_*`, model + integration error) and against the tight run of the
same mode and mu (`ref_self_*`, integration error only).

### Findings

1. **Smoothing error decays like 1/mu and the runtime knob closes the model
   gap.** The smooth trajectory's deviation from the pinned exact-model
   reference falls monotonically over four decades of mu (TwoBusGensal:
   1.4e-1 at mu = 1 to 7.1e-5 at mu = 1e4; TwoBusIeeet1: 3.2e-2 to 3.3e-5)
   while the piecewise arm sits at its integration-error floor (2e-6 to
   8e-6). At mu = 1e4 the smooth model is within roughly an order of
   magnitude of that floor. `figures/error_vs_mu.png`

2. **Exactness costs Newton work.** The pinned piecewise arm needs more
   Jacobian evaluations than the smooth model at every swept mu on WECC240
   (199 vs 58-160) and more nonlinear iterations on the small cases; the
   smooth family's own work also grows with mu (WECC240 Jacobians triple
   from mu = 100 to mu = 1e4). Sharpness is paid for in either family.
   `figures/work_vs_mu.png`

3. **At scale the exact-gate model is not integrable through a fault
   without event handling; smoothing is what makes it feasible.**
   ACTIVSg10k (71k states): the smooth model completes 10 s of simulation
   in 11.2 s wall at mu = 100 (1304 steps) and 16.7 s at mu = 1e4 (1728
   steps). The pinned piecewise model integrates cleanly to the fault (110
   steps, zero failures), thrashes through the fault window (dozens of
   corrector failures in 0.1 s of simulated time), and stops a few
   milliseconds after fault clearing with h at hmin. The step-size trace
   shows the collapse directly. `figures/activsg10k_step_collapse.png`

4. **Very shallow smoothing breaks initialization on stressed cases.** At
   mu = 1 the smooth WECC240 and ACTIVSg10k models fail verification during
   SystemModel allocation (REPCA PI limits, saturation seeds), while the
   piecewise WECC240 arm, whose exact-init inverses are sharpness
   independent, initializes and completes. The smooth family's usable mu
   range is bounded below on realistic cases.

5. **Control case.** ThreeBusBasic (unsaturated GENROU, no active
   primitives) produces identical counters in both arms, confirming the
   families differ only where limiter/saturation primitives are active.

Caveat: the ACTIVSg200/500 trajectory errors (1e-2 to 1e0) are dominated by
phase drift of sustained inter-area oscillations over the 10 s horizon; the
pointwise WRMS metric overstates model disagreement there. The per-mode
`ref_self` columns carry the same signature, so mode comparisons on those
cases should lean on the work counters rather than raw trajectory error.

## Provenance

Branch `lukel/smooth-paper-dev`. One binary for every run; mode, mu, and
gate_mu are runtime study-file settings, so no per-point rebuilds (contrast
with the older `scripts/HICSS` sweep, which patched `MU` and rebuilt per
value).
